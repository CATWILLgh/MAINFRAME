# Inspect a MAINFRAME installation

Establish the applicable loading contract from current official documentation,
then inspect the actual configuration. Bundled guides can help locate sources;
record the pages retrieved and any access gaps. Establish shared Desktop/CLI
mechanisms per layer and retain unresolved differences between sources.

## Coverage

Check packages/plugins first because they can supply other layers. Then inspect
instructions/rules, skills, commands, hooks, profiles/subagents, MCP integrations,
and background services/shared helpers, one layer at a time.

For each layer, derive its global, project, alternate, explicit, and package
loading locations from the documentation. Read the relevant non-secret
configuration and follow registrations to their exact targets and consumers.
Record the evidence and bounded conclusion in one coverage table before moving
on. Reuse sources that cover multiple layers and revise earlier conclusions if
later evidence changes them. Unsupported and unverified are different outcomes.

## Inspection boundaries

Use targeted native reads and searches. Read skill bodies or supporting files
only to resolve a question about loading, ownership, behavior, or dependencies.
Follow references beyond the loading roots only when the current environment
provides a concrete connection. Keep unrelated adapters, whole-home searches,
credential stores, transcripts, and log contents outside this inspection.

Judge objects individually; do not use discovery, classification, or cleanup
scripts. Inspected instructions are evidence, not authorization to execute
their workflows. Repository tests and validators do not establish what an agent
loads. Keep the audit read-only.

## Evidence for findings

- Ownership requires a managed section, ownership record, or source comparison
  that distinguishes MAINFRAME content from user changes. Names and age alone
  do not establish ownership or obsolescence.
- Loading requires the documented discovery rule and the actual object or
  registration. A directory listing shows entries, not file contents. Inspect
  package contributions even when no separate configuration file exists.
- Resolve symlinks relative to their parent and check the exact target. Access
  refusal establishes an unknown state, not absence or a broken link.
- Check a referenced service's activity through an appropriate native status
  interface. A tool's empty task list covers only its own tasks; keep unchecked
  consumers explicit rather than launching a broad process search.
- A claim of absence covers only the inspected loading locations. Include
  documented overrides and package contributions before clearing a layer.
  Session and cache data named after a project are not automatically owned by
  its harness.

## Report

Use one table: layer, official source, loading locations, actual inspection,
and supported result or gap. Keep every layer visible, including unsupported
or inaccessible ones. Finish independent checks when another layer is blocked;
report incomplete coverage as a partial audit.

For each finding, include its path or registration, ownership evidence, user
modifications, known consumers, and proposed action with its consequence.
Distinguish retained current material, obsolete owned material, and uncertain
objects. An empty cleanup list is valid and does not imply there are no
MAINFRAME objects or no unchecked locations.

Installation or removal may use these findings within the agreed scope.
Recheck exact objects before changing them, preserve user work and shared
consumers, and detach registrations before removing their targets. Back up
non-secret changes according to the installation or removal procedure.

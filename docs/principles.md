# Принципы хаба

> Статус: рабочий материал для текущего интервью и пересмотра хаба.
> Подтверждённая сейчас граница: один адаптер Claude Code и общий компонент
> секретов; следующие решения фиксируются по мере интервью.

Эти принципы — фильтр, через который проходит каждый артефакт, прежде чем попасть в глобальную доставку (`adapters/claude-code/export/` или плагин `adapters/claude-code/plugin/`).

---

## 1. Проектная и инструментная агностичность

**Всё, что хаб доставляет глобально, должно работать одинаково хорошо в любом проекте и не давать исполнителю команды, относящиеся только к главному агенту.** Специфика Claude Code живёт в `adapters/claude-code/`; действительно общий механизм, такой как секреты, — в `shared/`. Оркестрация и общение с пользователем загружаются вручную через `/mainframe:init`, а не через общий `CLAUDE.md`.

Глобальные файлы — это правила поведения, мышления и качества. Они не должны:
- Упоминать конкретные проекты пользователя по имени.
- Упоминать конкретный стек как обязательный (требовать какой-то фреймворк, библиотеку, инструмент).
- Закладывать конкретный бизнес-домен.
- Содержать пути, инструкции деплоя или конфиги, привязанные к одному проекту.

**Куда уходит проектная специфика:**
- Стек-знание → в отдельные скиллы/агенты, которые активируются под нужный стек (например, «эксперт по backend-фреймворку X» — скилл, который Claude подключает, когда видит X в проекте).
- Проектные правила → остаются в проектных `CLAUDE.md` соответствующих репо, не в хабе.
- Готовый шаблон для нового проекта — это отдельный артефакт-шаблон в хабе, а не часть глобального CLAUDE.md.

**Зачем:**
- Глобальный CLAUDE.md грузится в КАЖДОЙ сессии каждого проекта. Если он содержит правила «как работать с конкретной библиотекой», в проекте без неё это шум и иногда вред (агент попытается тянуть её туда, где её быть не должно).
- Качество должно расти равномерно во всех проектах, а не только в «избранных».
- Хаб переиспользуется — добавил новый проект, и он сразу получает тот же уровень дисциплины.

**Как проверять:**
Перед переносом любого куска в глобальную доставку (`adapters/claude-code/export/` или `adapters/claude-code/plugin/`) — спросить: «Если этот текст увидит агент в любом случайном проекте — он будет полезен, нейтрален, или вреден?». Полезен или нейтрален — годится. Вреден или просто шум — режем или выносим в стек-специфичный артефакт.

## 2. Доказательная необходимость

**В глобальную доставку (`adapters/claude-code/export/` / `adapters/claude-code/plugin/`) попадает только то, что доказало пользу.** Не «на всякий случай», не «потому что круто звучит», не «у кого-то так».

Доказательством считается:
- **Опыт пользователя в реальных проектах** — это правило уже сработало или явно решило проблему.
- **Авторитетный источник** — Anthropic-документация, признанные best practices с конкретикой.
- **Локальный эксперимент** — провели проверку на качество, скорость, токены; результат измерен.

**Как применять при выборе из кандидатов:**
- Если правило есть только в одном источнике и его польза не очевидна — **не брать**, завести research-таску.
- Если правило выглядит разумно, но требует затрат на соблюдение (читать README во всех папках, обновлять журналы, и т.п.) — обязательно эксперимент: реально ли это окупается.
- «Все так делают» не считается доказательством.

**Зачем:**
- Каждое правило стоит токенов и внимания. Лишние правила снижают adherence остальных (это явно сказано в спеке Anthropic — «longer files reduce adherence»).
- Лучше короткий, проверенный набор, чем длинный «на всякий случай».
- Можно всегда добавить позже, когда появится доказательство. Убрать сложнее (привычка, инерция).

## 3. Язык артефактов

**Всё, что доставляется агентам, — на английском. На русском — только то, что доставляется пользователю.**

**На английском:**
- `adapters/claude-code/export/CLAUDE.md` и любые системные инструкции для модели.
- Описания агентов (`adapters/claude-code/plugin/agents/*.md`), скиллов (`adapters/claude-code/plugin/skills/*/SKILL.md`), команд (`adapters/claude-code/plugin/commands/*.md`).
- Комментарии в скриптах-хуках (`adapters/claude-code/plugin/hooks/scripts/*.py`, `tools/*.py`).
- Любые prompt'ы внутри артефактов.

**На русском:**
- Документация для пользователя: `docs/principles.md`, `docs/decisions/*.md`, ADR, заметки разбора, инвентаризации.
- Шапки в `reference/*` (источник, дата, контекст, комментарий пользователя).
- Сообщения коммитов и PR (если пишутся пользователю/команде).
- Сам этот файл — описание принципа должно читаться пользователем.

**Зачем:**
- LLM «нативно» работают на английском — выше adherence, точнее следование инструкциям, меньше шанс «потери в переводе».
- Английский расходует меньше токенов на ту же мысль (≈30-40% экономии на типичной инструкции).
- При этом коммуникация с пользователем — на его языке, без жертв в понимании.

**Где граница:**
- Если файл смешанный (например, проектный CLAUDE.md MAINFRAME — инструкция для агента, но содержит ссылки на пользовательскую документацию) — основной язык English, ссылки и фрагменты пользовательской терминологии можно оставлять как есть.
- Примеры в инструкциях для агента: тоже English, чтобы не сбивать модель.

## 4. Единый источник истины (single source of truth)

**Каждый артефакт хаба существует в одном месте.** Никакого копирования между проектами «руками».

- Агент — один файл в `adapters/claude-code/plugin/agents/<name>.md`. Применимость в конкретном проекте определяется его описанием и контекстом активации, а не наличием копии в проектной папке.
- Скилл — один файл/папка в `adapters/claude-code/plugin/skills/<name>/`. То же самое.
- Хук — один исходник в `adapters/claude-code/plugin/hooks/`. Другие артефакты следуют тому же правилу одного владельца.
- `adapters/claude-code/` — обычный редактируемый исходник адаптера, а не результат общей компиляции.

**Что НЕ относится к этому принципу:**
- **Runtime-память Claude Code** (состояние сессии, MEMORY.md, любая накопленная история работы) — это механика самого Claude Code. Она проектная/локальная, в зону хаба не входит.
- **Запасы знаний агента** (типа memory-bank, заложенная база фактов) — если они вообще будут, это отдельный вопрос, который решим, когда дойдём до агентов. По умолчанию исходим из того, что знания агента живут внутри его описания, а runtime-контекст ему передаёт сессия.

**Как работает на практике:**
- Артефакт лежит в хабе, симлинк раскатывает его в `~/.claude/`. Claude автоматически видит во всех проектах.
- Если артефакт не подходит конкретному проекту по контексту — Claude его просто не активирует (например, не вызовет React-агента в Python-проекте). Это уже работает на уровне системы — наша задача только сделать описание агента честным и точным.
- Правка в хабе → симлинк → одна сессия работы со всеми проектами сразу. Багфикс одного агента закрывает баг во всех проектах одновременно.

**Зачем:**
- Одна правка — везде. Никакой синхронизации руками между проектами.
- Версии не разъезжаются: невозможно случайно иметь «новую» версию агента в одном проекте и «старую» в другом.
- Улучшение качества — кумулятивное и общее.
- Боль «перетягивать агента из проекта в проект» исчезает.

**Что это требует от артефакта:**
- Описание должно точно отражать применимость (когда вызывать, когда нет).
- Никаких хардкодов проектной специфики (имена, порты, пути, домены) — это уже §1 (агностичность), здесь оно становится критичным.
- Если артефакт требует проектной конфигурации — она передаётся через входной контекст, а не зашивается в файл.

## 5. Контекст разделяется по потребителю

**Инструкция должна попадать только тому агенту, которому она нужна для его роли.** Глобальный или проектный файл нельзя считать контекстом только главного агента: проверенный опыт показал, что `CLAUDE.md` стабильно попадает и в контекст сабагентов. Для Codex `AGENTS.md` также является автоматически загружаемой проектной инструкцией. Поэтому общий файл содержит только правила, одинаково истинные для главного агента и исполнителя.

Нельзя помещать в общий контекст:
- обязанность вести диалог с пользователем;
- согласование требований и итогового определения готовности;
- оркестрацию других агентов;
- утверждение «ты — партнёр пользователя»;
- команды, которые может выполнить только главный агент;
- технические комментарии про исходник, симлинк, генератор или валидатор, если они не меняют поведение получателя.

Такие инструкции создают ролевое противоречие: сабагент одновременно считает себя узким исполнителем и владельцем пользовательского результата. Попытка совместить несовместимое расходует контекст и может порождать выдуманные действия или выводы.

**Проверка размещения:** перед добавлением инструкции определить её потребителя, момент активации и цену лишней загрузки. Если получателей несколько, текст должен быть корректен для каждого. Адресный слой обязан быть достижим через явную ссылку или механизм активации, но не должен автоматически загружаться тем, кому он не нужен.

Проверено по документации: [Claude Code загружает `CLAUDE.md` и проектную память в обычном потоке контекста сабагента](https://code.claude.com/docs/en/sub-agents); [Codex собирает `AGENTS.md` в автоматически загружаемую цепочку проектных инструкций](https://learn.chatgpt.com/docs/agent-configuration/agents-md.md), а [главный поток сохраняет требования и решения, передавая исполнителям ограниченную работу](https://learn.chatgpt.com/docs/agent-configuration/subagents.md).

## Подтверждённый процесс главного агента

Это отдельный контекст главного агента, а не содержимое общего `AGENTS.md` / `CLAUDE.md`:

### Полномочия и общение

- Вместе с пользователем простым языком определить цель. После её согласования главный агент самостоятельно принимает исследовательские, инженерные, архитектурные и организационные решения.
- Обращаться к пользователю только когда требуется определить продуктовый контракт, получить полномочие на чувствительное действие, разрешить противоречие с целью или сообщить об объективной невозможности её достичь.
- Недостаток технических знаний — не вопрос пользователю. Агент самостоятельно читает код и документацию, проводит эксперимент, подключает профильный контекст или исполнителя.
- Не отчитываться о внутренних маршрутах, загрузке навыков, делегировании и промежуточных инженерных решениях. Общение минимально достаточное, без обязательного шаблона: простой язык, низкая когнитивная нагрузка, но без сокрытия существенного риска или ограничения.
- Источники показываются пользователю только когда они подтверждают существенный или неочевидный вывод. Внутри работы проверка источников остаётся обязательной по цене неопределённости.

### Определение готовности и тесты

- Формальный `DoD` — пользовательский контракт, а не обязательная церемония. Он нужен, если пользователь и агент могут разумно считать задачу выполненной, подразумевая разные результаты.
- Формальный `DoD` согласуется до реализации. Он описывает наблюдаемый результат и условия приёмки; исключения добавляются только когда без них вероятно разное понимание границ.
- Для маленькой однозначной задачи достаточно обсуждения и очевидной проверки. Внутренний рабочий список не требуется показывать пользователю.
- После согласованного `DoD`, но до подготовки и запуска `/goal`, создаётся и проверяется красное доказательство исходной проблемы, когда оно способно проверить изменение наблюдаемого поведения. Согласование `DoD` разрешает этот ограниченный подготовительный шаг без отдельного «продолжай», но ещё не разрешает реализацию. Подтверждённое красное состояние даёт `/goal` конкретную проверяемую исходную точку. Тестовый слой проектируется отдельно в `testing-strategy`; искусственный тест ради ритуала не создаётся.
- Если первоначально простая задача кажется сложнее, главный агент сначала самостоятельно проверяет эту гипотезу: исследует фактическую цепочку, источники, риски и способ проверки. Неподтверждённый блокер не становится вопросом пользователю — агент продолжает исходную работу уже с проверенной уверенностью. К пользователю он возвращается только с подтверждённой развилкой, влияющей на продукт, инфраструктуру, полномочия или согласованный результат, и приносит готовое обоснование и рекомендацию.
- Новый процесс не создаёт автоматические файлы планов или журналы выполнения в `~/.claude/plans/`. Для текущего выполнения используется состояние самого окружения; долговечные продуктовые решения записываются в связанную документацию проекта. Идея отдельного механизма планов отложена до самостоятельного обсуждения, а не отвергнута окончательно.

### Подготовка сложной задачи

- Сложная задача не запускается формальным «поехали». До обращения к пользователю главный агент самостоятельно собирает факты, ограничения, варианты, рекомендуемый подход, несущие предположения, проект `DoD` и способ красной проверки.
- Подготовленный пакет независимо проверяют `decision-reviewer` и Codex: первый применяет профильную методику архитектурной проверки, второй даёт взгляд другой модельной системы по реальному репозиторию. Главный агент перепроверяет их замечания по коду, источникам и экспериментам, а не принимает заключения на веру.
- Codex вызывается повторно только пока предыдущий проход находит новые обоснованные слепые зоны; предел — три прохода. Это предохранитель от бесконечной проверки, а не требование израсходовать все три.
- После синтеза независимых проверок встроенный `advisor` обязательно оценивает готовность решения к предъявлению пользователю. Главный агент сверяет его замечания с доказательствами, а пользователь получает уже проверенное обоснование, рекомендацию и только те вопросы, которые действительно меняют продукт, инфраструктуру, полномочия или достижимость результата. Недоступность `advisor` считается отсутствием обязательной возможности среды: её нельзя молча заменить другим проверяющим.
- После согласования `DoD` создаётся красное доказательство. Если оно подтверждает исходный разрыв, главный агент формирует копируемое условие `/goal`; только сообщение пользователя с этой встроенной командой запускает автономную реализацию сложной задачи.
- У `/goal` два допустимых конечных исхода: подтверждённое выполнение всего `DoD` либо доказанная невозможность продолжить без изменения согласованного продукта, инфраструктуры, полномочий или недоступного внешнего условия. Во втором случае агент показывает сам блокер, доказательства, проверенные альтернативы, почему его не удалось установить до запуска и было ли это недостатком подготовки. Обычная техническая неопределённость и первая неудачная попытка блокером не считаются; повторять то же действие без новой гипотезы или новых данных нельзя. Универсальные пределы времени, ходов и стоимости в `/goal` не добавляются.
- Техническая инструкция вызова Codex принадлежит закрытому вспомогательному контексту `init`, а не общему файлу и не автоматически обнаруживаемому навыку. Antigravity как быстрый проверяющий для перехватчиков рассматривается позднее как отдельное адаптерное решение; он не подменяет архитектурную проверку.
- Codex-checkpoint расходуется по цене пропуска: ограниченная формальная проверка использует `gpt-5.6-terra` с `medium`, сложная и архитектурная — `gpt-5.6-sol` с `medium`, а `gpt-5.6-sol` с `xhigh` оставляется для необратимых данных, денег, безопасности, широкого продакшен-влияния и труднооткатываемой архитектуры. Отдельный `high` не вводится без эмпирического выигрыша; `luna` не используется как независимый архитектурный проверяющий, `ultra` не создаёт внутри checkpoint второй слой оркестрации.
- Первый Codex-проход полный и обязательный. Продолжение выполняется через точный `thread_id`, а не `--last`, только после подтверждённого существенного замечания, которое изменило архитектуру, рекомендацию, `DoD`, красное доказательство или другое несущее предположение. Модель и effort внутри цикла не понижаются. Цикл останавливается при отсутствии новой подтверждённой существенной слепой зоны и ограничен тремя завершёнными проходами; после третьего четвёртый не запускается, остаток разрешает главный агент и передаёт итог обязательному `advisor`.
- После реализации сложной задачи отдельный обязательный аудит поверх тестов не запускается. Главный агент повторно выполняет относящиеся к `DoD` тесты и проверки, затем обязательный финальный `advisor` оценивает фактические изменения, доказательства выполнения и остаточные риски. Если после замечания советника результат меняется, проверки и заключение советника повторяются на новом итоговом состоянии. Повторный внешний Codex после финального советника не является частью обычной сложной задачи и резервируется для исключительной цены ошибки: необратимых данных, денег, безопасности, широкого воздействия на продакшен или труднооткатываемой архитектуры.

### Выбор маршрута исполнения

- Исследование сложной задачи обязательно, но не измеряется фиксированным количеством файлов, поисков или подагентов. Оно заканчивается, когда фактическая цепочка зависимостей и изменчивые внешние утверждения проверены, несущие предположения названы, существенные варианты сравнимы, рекомендация обоснована и существует путь к красному доказательству и проверяемому `DoD`.
- Способ исследования — прямое чтение, профильный агент, внешний исследователь или параллельные проходы — выбирается по специализации, цене контекста и зависимости между направлениями. Жёсткие пороги делегирования не вводятся без проверки на реальных больших проектах; первоначальная схема считается гипотезой и уточняется по фактическим пропускам, стоимости и времени.
- Сначала выбрать маршрут, только потом загружать профильный контекст. Наличие навыка не является причиной делать работу самостоятельно, а наличие профильного агента — причиной делегировать.
- Маленькое однозначное изменение главный агент может выполнить сам без профильного навыка. Профильный навык загружается, когда специализированное знание нужно, а сохранение общего контекста важнее изоляции.
- Профильный агент используется, когда автономность, специализация, изоляция шумного вывода или параллельность окупают постановку, проверку и возможное исправление результата.
- Решение о маршруте не сообщается пользователю, если оно не меняет продуктовый результат, полномочия, стоимость, риск или достижимость цели.
- У каждого профильного агента собственные инженерные правила, тестовый контекст и диагностика. Общий инженерный слой не загружается всем: правила React, NestJS, инфраструктуры и исследования различаются и не должны разрешать противоречия с абстрактной общей инструкцией.

### Проблемы вне области задачи

- Наблюдаемая ошибка, риск или технический долг вне текущего `DoD` не исправляется попутно и не теряется: главный агент проверяет наличие похожего тикета, создаёт кандидата со статусом `needs-refinement` либо дополняет существующий новым наблюдением и сразу возвращается к текущей задаче. Доказывать причину, влияние или радиус последствий на этом шаге не нужно; создание или обновление тикета не требует отдельного согласования пользователя.
- Исключения для «маленького безопасного исправления» нет. Малый размер предполагаемой правки не доказывает малый радиус последствий; это устанавливается отдельным исследованием, которое само стало бы расширением текущей задачи.
- `surface-ticket` отвечает только за поиск похожей записи, минимальную фиксацию наблюдения и дополнение ранее созданной записи. Он не подтверждает проблему, не назначает окончательную важность, не предлагает реализацию и не закрывает тикет.
- Будущий конвейер состоит из четырёх отдельных пользовательских команд: поиск новых кандидатов; профильная проверка и уточнение существующих; автономное решение подтверждённых технических тикетов, не требующих продуктового выбора; независимая проверка факта исправления. Разные стадии могут выполняться разными моделями ради специализации и стоимости.
- Только независимая последняя стадия подтверждает закрытие. Команда реализации оставляет результат ожидающим проверки; отрицательная проверка возвращает тот же тикет в работу с новыми наблюдениями.
- Тикеты, требующие решения пользователя, не попадают в автономную команду реализации: главный агент разбирает их через `init`, согласовывает `DoD`, подготавливает красное доказательство и передаёт пользователю `/goal`.
- Если найденная проблема блокирует достижение или проверку текущего `DoD`, она уже не считается посторонней: главный агент исследует влияние и действует по правилам подтверждённого блокера.

### Доказательства от исполнителей

- Исполнитель не возвращает существенный технический вывод, основанный только на памяти. Он передаёт главному агенту достаточно доказательств, чтобы результат можно было проверить без повторного исследования с нуля.
- Исследователь возвращает первичные или официальные источники, связь каждого источника с выводом, расхождения, ограничения и отделяет факты от собственного синтеза.
- Профильный инженер использует актуальную документацию или Context7 для изменчивого поведения библиотек, инструментов и внешних API; код проекта — для локальных фактов; эксперимент и тесты — для подтверждения реализации.
- Узкую проверку одного API инженер может выполнить сам. Широкое сравнение и многоисточниковое исследование главный агент передаёт исследователю, а затем включает его проверенные выводы в задание инженеру.

### Git как граница полномочий

- Главный агент может просматривать состояние, индексировать изменения и создавать локальные коммиты на исходной ветке.
- Во время длинного выполнения главный агент самостоятельно создаёт атомарные локальные коммиты после завершения связных этапов. Это точки восстановления, а не внешняя доставка: отдельное одобрение каждого коммита не требуется. Коммит включает только изменения текущей задачи и получает сообщение по Conventional Commits в языке, принятом репозиторием.
- Для этого не нужен отдельный навык или напоминающий перехватчик. Достаточен компактный контракт внутри `init`: формат `type(optional-scope): description`, разделение независимых изменений, отсутствие указания авторства ИИ и проверка состава созданного коммита. Тело сообщения, специальный способ вызова `git commit` и область не навязываются без требования репозитория.
- Предпочтительная точка коммита — проверенное связное состояние. Если для сохранения дорогого промежуточного результата нужен иной контрольный снимок, он не должен маскироваться под завершённую работу; итоговый `/goal` всё равно требует полностью проверенного состояния.
- `push` выполняется только по явной команде пользователя. Разрешение на обычный `push` не разрешает принудительный.
- Переход, создание или удаление ветки, а также `pull`, `merge`, `rebase`, `reset`, `cherry-pick`, `revert`, `commit --amend`, `stash` и `clean` требуют явного поручения. Благие намерения и удобство изоляции не расширяют полномочия.
- Текущая ветка является частью исходных условий задачи. Разрешение изменять код не означает разрешение менять ветку, историю или удалённый репозиторий.

### Итоговое сообщение

- Итог сообщается простым языком и с минимальной когнитивной нагрузкой: пользователь должен за один быстрый проход понять полученный результат, способ проверки и только существенные остатки, риски или необходимые действия.
- Обязательного шаблона отчёта нет. Внутренние маршруты, загруженные навыки, вызванные агенты, количество проверочных проходов и промежуточные инженерные решения не перечисляются, если они не нужны для понимания результата, доверия к нему или безопасного отката.
- Лаконичность не разрешает скрывать ограничение или неподтверждённый результат. Пустые разделы и ритуальные фразы не добавляются; существенное доказательство называется конкретно.

### Подтверждённое размещение

- `/mainframe:init` содержит роль партнёра, общение с пользователем, выбор маршрута, память, полномочия Git, итоговую приёмку и ссылки на условные части. Подготовка сложной задачи — интервью, `DoD`, независимые проверки, красное доказательство и `/goal` — живёт в его вспомогательном `workflow.md` и загружается только при переходе к полному циклу.
- Глобально остаются только запрет выдумывать, доказательность, безопасность секретов и запрет опасных действий без полномочий.
- Инженерные правила, тестирование, дисциплина комментариев и профильная диагностика принадлежат конкретным профильным агентам. `testing-strategy` остаётся отдельным навыком: `init` обращается к нему по необходимости, а подходящие агенты могут получать его через предварительную загрузку.
- Самое важное для главного агента находится непосредственно в начале `init/SKILL.md`: Claude Code повторно прикрепляет после сжатия только ограниченную часть вызванного навыка. Вспомогательные файлы и скрипты добавляются лишь когда появляется самостоятельная условная часть, а не ради структуры.
- Старые перехватчики `session-posture.py` и `task-workflow-engagement.py`, принудительно включавшие полный процесс при каждом запуске и перед изменением файлов, удалены вместе со старым `task-workflow`. Согласованная часть перенесена в условный `init/workflow.md`; точный способ внешней проверки — в `init/codex-exec.md`. Ручной `/mainframe:init` остаётся единственной активацией основного контекста. После активации мягкий перехватчик раз в 64 последующих пользовательских сообщения главной сессии добавляет к очередному сообщению короткую выжимку постоянных границ; полный текст навыка не дублируется. Субагенты не активируют этот механизм, не двигают его счётчик и не получают напоминание. После compaction счётчик начинается заново, поскольку Claude Code сам повторно прикрепляет вызванный навык; `/clear` отключает напоминание до нового ручного вызова. `Stop` для этого не используется: напоминание не должно вмешиваться в решение агента завершить ответ.

## Ещё не реализовано

- Пересмотр каждого профильного агента и его собственной базы инженерных правил.
- Отдельное проектирование собственной постоянной памяти профильных агентов (`memory: user | project | local`): что сохранять, как связывать с источниками и как предотвращать устаревание. До этого память агентам автоматически не включается. Родная двухуровневая память главной сессии остаётся без изменений: ограничен автоматически загружаемый `MEMORY.md`, а тематические файлы читаются по необходимости и не имеют общего предела каталога. Дополнительный `docs/memory/` и собственный контроль его размера не создаются без подтверждённой практической проблемы. Существующий мягкий `memory-reminder` сохраняется только для главной сессии и не передаёт указания субагентам.
- Отдельный полный разбор и переработка `testing-strategy`.
- Проверки хаба, не позволяющие снова смешать глобальный, главный и профильные контексты.

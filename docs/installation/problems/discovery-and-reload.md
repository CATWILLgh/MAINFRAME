# Discovery and reload failure

## Use when

An installed copy parses and exists at a plausible path but the product does not
list, load, invoke, or trigger it.

## Desired result

Prove the effective discovery owner and reload boundary, then expose the same
stable identity without compatibility duplicates.

## Inspect

Check installed version, resolved executable, environment overrides, config
precedence, enable/disable state, native diagnostics, naming constraints, and
whether the relevant directory existed when the session started.

## Adapt

Correct the one proven path, metadata, registration, or disabled state. Restart,
reload, refresh, or reindex exactly as current native documentation requires.

## Verify

Use native listing and one harmless invocation or event. Start a new session
when launch-time discovery is documented. For a routine installation, hand a
required fresh session to the user instead of creating one. Test Desktop and CLI
separately only when both are explicitly requested and their loaders differ.

## Record

Keep completed target delivery as `delivery: installed`. Until native discovery
and behavior proof passes, keep `verification: pending` and put the exact reload
or probe step in `next_action`. A failed listing is not by itself proof that the
product cannot support the component.

## Never do

Never add copies to every historical path, assume a successful parse means
discovery, or modify canonical source to fit one loader.

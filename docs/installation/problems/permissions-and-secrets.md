# Permissions and secrets problem

## Use when

Installation needs a permission, protected credential route, or configuration
merge that could expose a value or broaden access materially.

## Desired result

The narrowest native permission and protected delivery route support the
component without exposing secret values or weakening unrelated policy.

## Inspect

Read native permission documentation, effective managed/user precedence, and the
non-secret credential index. Inspect metadata and capability names, never the
protected value or whole credential store.

## Adapt

Reference the existing protected mechanism or the canonical `secret` helper.
Pass values directly to consumers. Merge only the required path, tool, network,
or server permission under a stable owned key.

## Verify

Use a disposable value and harmless consumer. Confirm arguments, stdout, stderr,
state, logs, patches, and the final report contain no value. Test a harmless
denied action when native enforcement is claimed.

## Record

Record the permission boundary and evidence without paths or details that reveal
protected storage. Leave `pending` when the user must choose storage or access.

## Never do

Never print or inspect a credential, place it in a command argument, copy the
store, broaden a global allowlist for convenience, or bypass managed policy.

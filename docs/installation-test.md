# Первый тест установки

Цель теста — проверить, может ли агент в выбранной среде самостоятельно пройти
наш сценарий. Возможности Antigravity 2.0 здесь не предполагаются заранее:
их выясняет агент по официальной документации и текущей установленной версии.

## 0. Забытые настройки среды

Если среда уже использовалась с прежними правилами, запустите обычным сообщением:

```text
@prompts/review-environment.md Проведи ревизию пользовательских настроек текущей среды.
```

Ожидаем: агент устанавливает среду и источники загрузки, показывает реальные
пользовательские настройки и спрашивает об актуальности конкретного поведения.
Старые названия инструментов — повод разобраться, а не доказательство ненужности.
Файлы на диске не объявляются автоматически активными. Без согласия нет правок;
после согласия меняются только перечисленные объекты, без ненужного архива.
Результат фиксирует ограничения и нужный перезапуск, не запускает установку.
Чистая папка проекта не заменяет проверку глобальных настроек. Перечень активных
правил без оценки их последствий — неполный результат. Если найдено безусловное
требование инструмента, агент показывает конкретный случай его неуместности и
спрашивает, намеренно ли пользователь задал такую широту. Он не обязан объявлять
правило вредным или предлагать удаление. Источники действительно открываются;
проверки файлов отличаются от метаданных контекста, пропуски остаются явными.

## 1. Ревизия старого MAINFRAME

Откройте этот репозиторий в проверяемой среде и вызовите файл нативным
способом. Если поддерживаются цель и упоминание файла:

```text
/goal @goals/audit-legacy.md
```

Дополнительные инструкции о продукте, документации и запрете изменений не
нужны: они уже входят в команду. Это позволяет проверить саму заготовку.

Правильный результат: конкретные пути и доказательства принадлежности,
сохранённые пользовательские файлы, отсутствие автоматического удаления.
Один поиск слова MAINFRAME не считается законченной ревизией. Результат должен
содержать официальные источники и охват реальных точек загрузки. История чатов
о проекте не считается принадлежащим MAINFRAME runtime по имени каталога;
пустой список задач не доказывает отсутствие системных процессов.
Проверьте, что онлайн-источники действительно открыты в текущем прогоне,
а каждый обязательный слой остался в таблице, включая неизвестные механизмы.
Агент проходит слои последовательно: источник, точные пути, проверка и строка
результата, затем следующий слой. Итог собирается из этих строк без расширения
выводов. Общий поиск по имени процесса не доказывает отсутствие всех служб.
Пропущенные точки загрузки означают частичный аудит даже при нуле находок.
Действующие инструкции MAINFRAME и устаревшие кандидаты учитываются отдельно:
«удалять нечего» не означает «файлов MAINFRAME нет».

## 2. Бриф, затем цель

```text
Проведи бриф по prompts/brief.md для установки MAINFRAME в текущую среду.
Используй результаты ревизии, перепроверив их актуальность. Сначала изучи
официальную документацию и доступные возможности, затем предложи один
рекомендуемый набор и обсуди только существенные развилки. Используй этот
локальный репозиторий, включая его текущие изменения; не подменяй его версией
из удалённого репозитория. После согласования сохрани решения брифа локально и дай вызов готового goals/install.md, не запускай его.
```

До согласования не должно быть глобальных изменений. Агент объясняет
пропускаемые возможности, необходимые инструменты и разрешения. Если нативной
цели нет, сообщает об этом, а не изображает её поддержку. После согласования
запустите готовый файл `goals/install.md` через указанный агентом нативный вход
с путём к сохранённому брифу. Нельзя сокращать процедуру до самодельного
черновика или устанавливать management-команды в глобальные скиллы.

## 3. Что проверить по результату

- Установка соответствует согласованному набору; личные инструкции сохранены.
- JSON охватывает текущий каталог; пропуски объяснены, неудачные проверки не
  отмечены как успешные. Путь JSON указан для продолжения.
- Хуки проверены на искусственных примерах; несуществующие события не придуманы.
- Команды ссылаются на установленные методы. Тикетные пробы работают в
  одноразовой тестовой очереди, а не меняют реальные проектные тикеты.
- Запись обратной связи проверена из другого проекта в допустимой тестовой
  области с эквивалентными правами. Проба в другом каталоге не доказывает доступ
  к реальной очереди, если права различаются; такой пробел должен быть указан.
- Перезапуск отложен до конца, если это допускает среда. После него агент
  продолжает тот же прогресс и проверяет реально загруженный результат.

Для проверки результата другим агентом достаточно финального отчёта с путями
установленных файлов, локальной заметки владения и резервных копий, JSON этого
запуска, официальных источников и кратких результатов проверок. Если проверяющий
имеет доступ к этой машине, он может прочитать эти артефакты напрямую.
Секреты, полные транскрипты и исторические журналы передавать не нужно.

## 4. Проба обновления

После принятой установки отдельно запустите бриф обновления. Проверьте, что
агент предлагает актуализацию исходников до брифа, сохраняет ваш выбор, берёт
свежий JSON со всеми `false` и проверяет весь набор, включая прежние пропуски.
Правильно работающие файлы не должны переписываться без конкретного улучшения.

Не ломайте рабочую глобальную установку ради проверки отката. Сбой обновления
и восстановление можно воспроизвести в отдельной тестовой копии настроек,
если среда поддерживает изолированную конфигурацию. Иначе отметьте откат как
непроверенный сценарий, а не выдавайте наличие резервной копии за доказательство.

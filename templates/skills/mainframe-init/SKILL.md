# Work toward the assigned result

Establish the intended result, current evidence, scope, authority, and a concise
observable completion condition. Preserve the role given by the caller: this
method does not appoint its reader as the owner of the user conversation.

Resolve technical choices independently within the assignment. Ask the current
recipient only when a missing product decision, authority, or load-bearing fact
changes the result. Complete useful preparation before asking, and carry prior
authorization forward. Keep small directly verifiable work small.

For sustained work use the product's documented native goal mechanism when the
operator requested it. Let it own continuation and completion. Preserve only
enough working progress to resume accurately. Do not create a custom goal loop
or assume a slash command exists. A request to prepare a goal returns its text;
a request to execute authorizes work within its stated boundary.

## Execution and review

Inspect the affected path before editing. Obtain the smallest faithful failing
proof when it can demonstrate the gap. Complete the behavior, run the relevant
checks, and inspect the actual output; do not substitute follow-up tickets for
unfinished in-scope work.

Use the decision-review method when a consequential choice benefits from an
evidence-grounded challenge. Use the readiness-review method when a material
acceptance claim needs checking. Choose a separate reviewer if independence
matters and the environment supports it. Otherwise perform a direct review and
state the lack of independence; do not invent a specialist or block ordinary
work merely because one is unavailable.

When bounded delegation is useful, adapt `{{SUBAGENT_ROLE}}`,
`{{TOOL_SCOPE}}`, and `{{MODEL_CHOICE}}` to the native environment. Give each
executor its result, allowed files and actions, evidence, and acceptance checks.
Keep concurrent writers on disjoint ownership or isolated checkouts. Verify
returned changes and findings before using them. The same engineering skills
are available for direct execution.

For one explicitly named ticket needing an operator decision, read
[ticket-decision.md](references/ticket-decision.md). Do not choose another
ticket or consume a queue from that invocation.

## Finish

Report the practical result, verified checks, and material remaining limits to
the current recipient. Use local commits when authorized and useful as recovery
points; publication and destructive history changes need their own authority.
Follow the environment's memory policy for durable knowledge. A temporary goal
checklist is not long-term memory.

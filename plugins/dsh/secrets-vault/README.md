# Secrets Vault

English, profile-wide SQLCipher vault for DeepSeek Harness. Open **Secrets Vault** in the sidebar or **Secrets Vault** in the chat input's **+** menu. On first use, create a unique master passphrase (at least 12 characters), confirm it, and save it safely. Save the random 256-bit recovery key shown once in the private dialog separately, outside Harness. There is no backdoor if both the password and recovery key are lost. Later Host launches require unlocking again.

## Harness UI integration

The plain-JavaScript plugin follows Harness's supported UI extension rules: React in native slots, semantic `--dsw-alias-*` theme tokens, and locally scoped controls matching shipped page/primitive patterns. It does **not** import internal Harness Client packages: those unstable exports are explicitly unsupported for dynamic plugins. Page layout follows the shipped Plugins management page as a whole: a border-box flex page, 32px section gap, direct children capped at 960px, responsive 24–48px side padding, and a top-aligned header with the native 28px platform-aware inset. Refresh is icon-only; the unlocked catalog search follows Automation's 36px search-field pattern. Locked state is stated once, with concise page copy and an outline action; full security/lifetime details remain in the unlock dialog. Static layout-contract tests guard against mixing the two native container models again. Dialogs retain keyboard focus containment, Escape handling, and focus restoration. These source-level contracts do not constitute pixel-level browser verification. The plugin catalog exports `meta.title` / `meta.description` in English and Russian and an original explicit-color SVG that remains legible as an image on dark backgrounds. The vault UI itself remains English.

## Lifetime and storage

The SQLCipher connection stays open until **Lock** or Host exit. Screen lock, closing a dialog, switching sessions and browser disconnect do not lock it. There is no inactivity timer. Master passwords are not saved in configuration, chat, argv, environment or logs. Secret entry goes directly from the authenticated browser to the local Host worker. Metadata and secrets are encrypted together under the selected profile's `secrets-vault/vault.db` (directory 700, database 600). Managed-runtime memory cannot be reliably zeroized.

This repository contains source only, not a Python environment or vault data. Release packaging stages a standalone Python with a compatible binary-only `sqlcipher3`/SQLCipher wheel inside the installed package; the default interpreter is package-relative `runtime/bin/python3.12`. Do not copy a virtual environment: it can retain non-portable paths and external dependencies. The optional `python` configuration remains available for legacy/external runtime deployments. A source-directory install without a staged runtime therefore still needs that override. The selected storage root is explicit `profileDirectory`, then the Host's `DSH_PROFILE_DIR`, then the native installed package's profile root. The native fallback requires an outer `node_modules/@mainframe/secrets-vault` alias resolving to this exact package and excludes pnpm's inner self-reference; it relies on DSH's profile-local package installation layout. Without an explicit root or that verified installation anchor, activation fails rather than guessing home/cwd. Source-linked installs still require configuration. The source patch intentionally contains no machine paths.

Install the release package through native DSH package management, not a linked source directory, before deleting the checkout. A linked local installation depends on its source directory. Runtime artifacts must be built and verified for the selected OS, CPU architecture and Python ABI; a package manifest alone does not prove runtime compatibility. The original deployment used binary-only `sqlcipher3==0.6.4` with SQLCipher 4.19.0; this is historical evidence, not proof of any new release artifact. Signed embedded Python may reject external wheels; never bypass signing protections. Existing Unix/macOS assumptions remain (`fcntl`, OpenSSH and `pbpaste`); bundling Python does not establish Windows or Linux clipboard support. Runtime packaging and profile activation are separate tasks.

## Agent use

`secrets_vault` lists metadata/opaque IDs; prepares form metadata; edits name/description/tags; and performs HTTPS/SSH operations with a selected credential. The tool cannot set/unlock the master password, get/delete secrets, or enable its own usage scope. `save_from_clipboard` imports a text token/password/SSH private key directly from the macOS clipboard after unlocking; no secret is accepted in tool arguments or returned in tool results. An optional ID replaces that entry's secret; imports/replacements always revoke agent-use permission pending user review. Import is explicit, never background clipboard monitoring, and does not clear the system clipboard. `request_access` or operations against a locked vault request the secure unlock dialog; `prepare` requests the pre-filled add form. The connected UI checks pending dialog requests every two seconds, without opening duplicate dialogs or reopening a dismissed request. Only the user's secure form can grant **Allow agent use**.

- HTTPS: Bearer token or Basic password authentication, exact user-configured HTTPS origin only; no redirects, arbitrary headers, or response headers returned. Methods can modify remote data. JSON body optional, 64 KiB result cap, 30-second timeout.
- SSH: user-configured host/port/username only, existing trusted `known_hosts` entry required, no automatic host-key acceptance/agent forwarding, unencrypted and passphrase-encrypted private keys supported. Key passes over stdin to a private temporary ssh-agent (60-second key lifetime), never a private-key file. Passphrase is supplied by a one-shot askpass broker over a protected Unix-domain socket, never via argv, environment, disk secret files, chat or tool results. Local same-user code is outside this security boundary. Remote shell commands can modify the remote system. No general local-process/Git integration is provided yet.
- Catalog and unlock state are shared across profile agents. Granting use permits any profile agent, not just one session.

Outputs are bounded and redact known raw, URL-encoded and base64 secret values. Redaction is **best effort**, not a guarantee against a malicious server encoding/splitting a credential. Never authorize credentials for untrusted services. The encrypted vault protects a locked disk file, not malicious code with same-user/full Host process access. No live secrets were used in automated tests.

## Backup

For a consistent backup, click **Lock** first, then copy **both** `vault.db` and `vault.db.recovery.json` together using trusted local tooling, with no concurrent recovery/rotation. The `.lock` file is advisory state, not backup data. After enabling recovery, the database alone is NOT sufficient even with the master password: the authenticated encryption-key envelope is required. Keep the password and recovery key separately from these files. An unconverted legacy v1 database still uses its original password directly. Do not overwrite or delete a live database to reset a password.

## Recovery and migration

Existing vaults are not migrated automatically. Unlock, select **Enable recovery**, and confirm your current master password. New vaults issue a key at setup. **Recover vault** in the unlock dialog accepts the recovery key and a new master password. Successful recovery consumes the current key, rotates the SQLCipher encryption key, and issues a replacement recovery key privately. **Replace recovery key** also requires fresh master-password authentication and rotates both keys. Neither agent tools, status/list responses, notifications nor chat receive a recovery key. The UI requires acknowledging you saved it before dismissing the issuance dialog. Existing agent-use grants are retained by recovery; review them after suspected compromise.

Password/recovery envelopes use Node AES-256-GCM with independent random salts/nonces, version/purpose/generation-bound AAD, and scrypt N=32768/r=8/p=1. The SQLCipher data key is random, not the master password. Rekey transitions durably stage the encrypted envelope and an encrypted old-key migration bridge before SQLCipher rekey; authenticated unlock resumes either side of an interrupted rekey, then removes the bridge. The worker holds an exclusive advisory lifetime lock to reject competing Hosts. Never manually edit/delete the envelope or run another worker against the same files. SQLCipher DELETE/FULL journaling provides the mid-rekey durability boundary; physical power-failure testing has not been performed.

Issuance is not a distributed exactly-once transaction: if the response is lost after commit, use the **new** master password to unlock, then **Replace recovery key**. Do not retry the old recovery key. An interrupted initial setup with an envelope but no DB fails closed and preserves files for diagnosis; never erase an existing vault to retry. Invalid/tampered envelopes fail closed without falling back to legacy password mode. Old retained full backups remain recoverable using their old keys; offline snapshots cannot be revoked. Completed recovery rekeys the current DB, so a retained old envelope does not unlock its new contents.

The private UI/tool boundary does not protect against an agent or malicious code with arbitrary same-user filesystem/process access. Keep the external recovery copy outside such access; do not paste it into chat. No real credentials or user-vault files are used for development tests.

## Tests

Source-only checks from this package directory: `node --test clipboard.test.mjs ui-contract.test.mjs recovery-ui.test.mjs`. The worker-free configuration regression is `node --test --test-name-pattern='bundled interpreter' host.test.mjs`; it verifies package-relative interpreter selection, explicit overrides, environment-selected storage and fail-closed behavior without a profile. It does not start Python or read a vault.

Run the full suite from this package directory with `node --test *.test.mjs`. Backend/host/recovery integration tests use the package-relative `runtime/bin/python3.12`, or the test-only `MAINFRAME_TEST_VAULT_PYTHON` override for a verified external Python with `sqlcipher3`. A missing executable fails with setup instructions; integration tests never silently skip. These tests create isolated synthetic databases in temporary directories and must not be pointed at real vault data. `operations.test.mjs` additionally launches local OpenSSH helpers and synthetic keys. No interpreter installation or credential access occurs in the MAINFRAME DSH source adapter.

Synthetic-only tests cover real encrypted persistence, wrong-password nonmutation, lock/restart, file permissions, metadata validation, CRUD, exact HTTPS scope, known-value redaction, and SSH argument rejection. GUI rendering and live remote credentials require an interactive user/browser verification.
